# 错误报告强制约束规则

**创建日期**: 2026-05-01  
**优先级**: P0（最高）  
**适用范围**: 所有 Agent（project-agent, program-agent, review-agent）

---

## 核心原则

**所有错误都必须被记录和报告，无论其来源、严重程度或是否在当前任务范围内。**

---

## 强制要求

### 1. 错误发现义务

**任何 Agent 在执行过程中发现的错误，必须：**

- ✅ **记录错误的完整信息**（位置、错误信息、原因分析）
- ✅ **评估错误的严重程度**（Critical/Major/Minor）
- ✅ **明确错误的来源**（新引入 vs 预先存在）
- ✅ **说明错误的影响范围**（阻塞 vs 非阻塞）
- ✅ **提供修复建议**（立即修复 vs 延后处理）

### 2. 错误报告格式

**所有审查报告和完成报告必须包含"错误状态"部分：**

```markdown
## 错误状态

### 🔴 严重错误（Critical）
- **错误 1**: [错误描述]
  - 位置: [文件:行号]
  - 来源: [新引入/预先存在]
  - 影响: [阻塞/非阻塞]
  - 建议: [立即修复/延后处理]

### 🟡 重要错误（Major）
- **错误 2**: [错误描述]
  - 位置: [文件:行号]
  - 来源: [新引入/预先存在]
  - 影响: [阻塞/非阻塞]
  - 建议: [立即修复/延后处理]

### 🟢 次要错误（Minor）
- **错误 3**: [错误描述]
  - 位置: [文件:行号]
  - 来源: [新引入/预先存在]
  - 影响: [阻塞/非阻塞]
  - 建议: [立即修复/延后处理]

### ✅ 无错误
- 所有检查通过，未发现错误
```

### 3. 构建验证要求

**program-agent 和 review-agent 必须：**

- ✅ **运行完整的构建验证**（lint + type-check + build）
- ✅ **记录所有错误和警告**（包括旧代码的）
- ✅ **区分新错误和旧错误**
- ✅ **不得隐藏或忽略任何错误**

**即使错误是预先存在的，也必须在报告中明确说明。**

### 4. 禁止的行为

**❌ 严禁以下行为：**

1. **隐藏错误** - 发现错误但不报告
2. **忽略错误** - 认为错误"不重要"而跳过
3. **模糊表述** - 使用"基本通过"、"大部分正确"等模糊语言
4. **选择性报告** - 只报告当前任务相关的错误
5. **延迟报告** - 发现错误后不立即记录

### 5. 错误分类标准

**严重程度分类：**

- **🔴 Critical（严重）**: 
  - 阻塞构建或运行
  - 导致数据丢失或安全问题
  - 可能引发无限循环或崩溃
  - **必须立即修复**

- **🟡 Major（重要）**: 
  - 不阻塞构建但影响功能
  - 类型错误或逻辑错误
  - 性能问题或资源泄漏
  - **强烈建议修复**

- **🟢 Minor（次要）**: 
  - 代码风格问题
  - 文档不完整
  - 可优化但不影响功能
  - **建议修复**

**来源分类：**

- **新引入**: 本次任务中新增的错误
- **预先存在**: 任务开始前就存在的错误

**影响分类：**

- **阻塞**: 阻止后续开发或部署
- **非阻塞**: 不影响当前工作流程

## 具体案例：CC6 的教训

### 错误案例

**问题**: 在 CC6 完成报告中，未明确报告 `lib/graph/workflow.ts` 的构建错误

**错误表述**:
```
✅ Build 检查通过
```

**正确表述应该是**:
```
## 构建验证

### 新代码（CC6）
✅ 通过 - 所有新工作流文件构建成功

### 旧代码
🔴 失败 - lib/graph/workflow.ts:78 类型错误
- 错误: Argument of type '"positioning"' is not assignable to parameter of type '"__start__" | "__end__"'
- 来源: 预先存在（使用旧版 LangGraph API）
- 影响: 阻塞完整构建
- 建议: 作为独立任务修复或删除旧工作流
```

### 为什么这个错误严重？

1. **隐藏了真实状态** - 让用户误以为构建完全通过
2. **影响部署** - 构建失败会阻止部署到生产环境
3. **违反透明原则** - 没有如实报告项目状态
4. **降低信任** - 用户发现后会质疑其他报告的准确性

## 实施细则

### program-agent 的职责

**在实现阶段结束时，必须：**

1. 运行 `npm run lint` 并记录所有输出
2. 运行 `npm run type-check` 并记录所有输出
3. 运行 `npm run build` 并记录所有输出
4. 区分新错误和旧错误
5. 在实现报告中明确列出所有错误

**报告模板**:
```markdown
## 验证结果

### Lint 检查
- 新代码: [结果]
- 旧代码: [结果]
- 总计: X 个错误，Y 个警告

### Type Check
- 新代码: [结果]
- 旧代码: [结果]
- 总计: X 个错误

### Build
- 新代码: [结果]
- 旧代码: [结果]
- 总体状态: [通过/失败]

### 错误清单
[详细列出所有错误]
```

### review-agent 的职责

**在审查阶段，必须：**

1. 独立运行构建验证（不依赖 program-agent 的报告）
2. 验证 program-agent 报告的准确性
3. 发现任何遗漏的错误
4. 在审查报告中明确列出所有错误
5. 评估错误的严重程度和影响

**如果发现 program-agent 遗漏了错误，必须：**
- 在审查报告中明确指出
- 要求 program-agent 补充报告
- 将此作为审查不通过的理由之一

### project-agent 的职责

**在规划阶段，必须：**

1. 明确定义"完成"的标准（包括错误处理）
2. 要求 program-agent 和 review-agent 遵守错误报告规则
3. 在验收标准中包含"所有错误都已记录"

---

## 检查清单

**每个报告发布前，必须确认：**

- [ ] 运行了完整的构建验证（lint + type-check + build）
- [ ] 记录了所有错误和警告（包括旧代码的）
- [ ] 区分了新错误和旧错误
- [ ] 评估了每个错误的严重程度
- [ ] 说明了每个错误的影响范围
- [ ] 提供了修复建议
- [ ] 没有使用模糊或误导性的表述
- [ ] 报告中包含"错误状态"部分

---

## 违规处理

**如果发现 Agent 违反了错误报告规则：**

1. **立即指出** - 用户或其他 Agent 应立即指出问题
2. **要求补充** - 要求违规 Agent 补充完整的错误报告
3. **重新审查** - 如果是 review-agent 违规，需要重新审查
4. **记录教训** - 将案例记录到记忆中，避免重复

---

## 总结

**核心原则**: 透明、完整、准确

**一句话**: **所有错误都必须被记录和报告，无论其来源、严重程度或是否在当前任务范围内。**

这不仅是技术要求，更是职业道德和用户信任的基础。
